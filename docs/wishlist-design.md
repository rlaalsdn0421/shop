# 찜하기 설계

상품 상세의 "찜하기" 버튼(지금은 비활성)과 상품 카드의 하트 자리를 실제로 동작하게 한다. **로그인한 사람만** 찜할 수 있고, 찜은 **계정(서버)에 저장**돼 다른 기기에서도 보인다.

## 1. 범위

| 한다 | 하지 않는다 |
|---|---|
| 상품 상세의 찜하기 버튼 동작(찜/찜 해제, 현재 상태 표시) | 옵션별 찜(찜은 **상품** 단위다) |
| 상품 카드(홈·목록·베스트·찜 목록)의 하트 | 찜한 상품의 가격 인하·재입고 알림 |
| `/wishlist` "찜한 상품" 페이지(보기·찜 해제), 헤더와 내 정보에서 들어가는 링크 | 비로그인 상태의 찜(브라우저에만 저장) |
| 계정 탈퇴 때 그 사람의 찜을 모두 삭제 | 찜 목록 공유, 폴더·정렬 바꾸기(최신 찜 순 고정) |

로그인하지 않고 하트를 누르면 로그인 화면으로 보낸다(장바구니와 같은 방식). 찜은 한 사람당 최대 200개다.

## 2. 데이터 (V21)

```sql
CREATE TABLE wishlist_items (
    user_id    VARCHAR(36) NOT NULL REFERENCES users(id),
    product_id VARCHAR(36) NOT NULL REFERENCES products(id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, product_id)
);
```

- 보조 인덱스는 두지 않는다. 기본 키 `(user_id, product_id)`가 모든 조회(항상 사용자 기준)를 받치고, 사용자당 행이 200개 이하라 정렬 비용이 없다. 인덱스를 하나 더 두면 찜을 누를 때마다 쓰기만 두 배가 된다. 상품 삭제 기능을 만들 때는 `product_id` 인덱스를 함께 추가해야 한다.
- 기본 키가 (사용자, 상품) 한 쌍이라 같은 찜이 두 번 생기지 않는다. 찜 추가는 `INSERT ... ON CONFLICT DO NOTHING`이라 여러 번 눌러도 안전하다(멱등).
- 새 테이블이라 기존 데이터·기존 쿼리에 영향이 없다. 마이그레이션은 한 번에 끝난다.

## 3. API (모두 로그인 필요, 응답에 `Cache-Control: no-store`)

| 요청 | 설명 |
|---|---|
| `GET /api/wishlist/ids` | 내가 찜한 상품 id 목록 `{ "ids": ["..."] }`. 하트 표시용이라 가볍다(최대 200개) |
| `GET /api/wishlist` | 찜한 상품 목록(최신 찜 순). 상품 목록 응답과 같은 항목 모양(`ProductListItem`). 한 번에 최대 200개라 페이지 나누기는 하지 않는다 |
| `PUT /api/wishlist/{productId}` | 찜하기. 이미 찜했으면 아무 일도 없이 성공(204). 없는 상품은 404, 한도(200개)를 넘기면 400 "찜은 최대 200개까지 담을 수 있어요." |
| `DELETE /api/wishlist/{productId}` | 찜 해제. 찜하지 않았어도 성공(204, 멱등) |

- 내 id는 로그인 토큰에서만 얻는다(`Authentication.getName()`). 요청으로 다른 사람의 찜을 읽거나 바꿀 방법이 없다.
- 찜 추가는 먼저 **사용자 행을 잠근다**(리뷰 등록과 같은 방식, 잠금 대기 3초). 그래서 한 사람의 찜 추가는 순서대로 처리되고 200개 한도가 정확히 지켜진다. 이 잠금은 외래키 검사(`FOR KEY SHARE`)와 충돌하지 않는 종류(`FOR NO KEY UPDATE`)라 주문 등 다른 기능을 막지 않는다. 탈퇴한 사용자는 401이다.
- 찜 변경(`PUT`/`DELETE`)에는 별도 속도 제한을 두지 않는다(인증 필요, 기본 키로 중복 불가). 남용이 보이면 `RateLimiter`를 건다.

## 4. 계정 탈퇴

`UserService.withdraw`가 계정을 지우는 같은 트랜잭션에서 그 사람의 `wishlist_items`를 모두 삭제한다(개인의 관심 상품 기록은 탈퇴 후 남길 이유가 없다). 탈퇴는 `USER` 역할만 가능하다(기존 규칙). 탈퇴 도중에 들어온 찜 추가가 삭제를 피해 행을 남기지 못하도록, 찜 추가가 사용자 행을 잠그고 탈퇴 여부를 확인한다(3절). 이 잠금 때문에 탈퇴 처리는 진행 중인 찜 추가가 끝나기를 기다리고, 그 뒤에 지운다.

## 5. 화면

- `WishlistProvider`(클라이언트 컨텍스트): 로그인 세션이 준비되면 `GET /api/wishlist/ids`를 **한 번** 불러 `Set`으로 들고 있다. `toggle(productId)`은 **낙관적으로** 화면을 먼저 바꾸고, 요청이 실패하면 되돌리고 안내한다. 같은 상품의 요청이 진행 중이면 다시 누를 수 없다. 로그아웃하면 비운다.
- `WishButton`(하트): 상품 카드와 상세에서 쓴다. 찜한 상태는 채운 하트, 아니면 빈 하트. 접근 가능한 이름은 상태와 상관없이 **고정**("찜하기 - 이름")이고 상태는 `aria-pressed`로만 알린다(이름이 "찜 해제"로 바뀌면 눌림 상태와 모순돼 읽힌다). 상세 버튼의 보이는 글자도 "찜하기"로 고정이다. 로그인하지 않았으면 눌렀을 때 `/login`으로 간다. `ids`를 아직 불러오는 중에는 비활성이다. 카드 하트의 터치 영역은 40px.
- 안내(실패·불러오기 실패)는 버튼마다 따로 두지 않고 `WishlistProvider`가 화면에 **하나만** 띄운다(아래쪽 작은 알림, `role="status"`). 찜 변경 실패 메시지는 5초 뒤 사라지고, 찜 정보를 못 불러왔다는 안내는 로그인 상태에서 계속 보인다. 카드가 40개여도 알림 영역은 하나다.
- 요청에 서버 응답이 없으면(시간 초과·네트워크) 처리됐는지 알 수 없으므로 되돌리지 않고 찜 id를 다시 불러와 맞춘다. 서버가 거절하면(400·404 등) 되돌리고 메시지를 보인다.
- 상품 카드: 카드 전체가 링크라 하트는 링크 **밖**(이미지 오른쪽 위에 겹쳐서)에 둔다. `ProductCard`는 서버 컴포넌트로 남기고 하트만 클라이언트 컴포넌트로 끼운다.
- 상품 상세: `AddToCartForm`의 비활성 "찜하기" 버튼을 `WishButton`으로 바꾼다.
- `/wishlist` 페이지: 로그인 필요(`useRequireRole`). `GET /api/wishlist`로 불러 `ProductCard` 격자로 보여 준다. **서버 목록이 기준**이다. 이 페이지에서 하트를 눌러 해제한 카드만 목록에서 바로 사라지고(다른 기기에서 찜한 상품이 이 기기의 옛 찜 목록 때문에 가려지지 않는다), 키보드 포커스는 제목으로 옮기고 "찜을 해제했어요"를 알린다. 비어 있으면 안내 문구와 홈 링크.
- 진입점: 헤더의 "찜" 링크, 내 정보 페이지의 "찜한 상품" 링크, 모바일 하단 탭에는 넣지 않는다(탭이 이미 가득하다).

## 6. 알고 두는 한계

- 찜 상태는 로그인 직후 `ids`를 불러온 뒤에 하트에 반영된다. 불러오는 동안은 하트가 비활성이다.
- 다른 기기에서 찜을 바꾸면 이 기기는 새로고침(또는 다시 로그인)해야 반영된다(주기적 동기화 없음).
- 품절·판매 중지 상품은 그대로 목록에 보인다(상품 삭제·판매 중지가 아직 없다).
- 찜 목록은 200개까지만 한 번에 내려준다.
