# 멈춘 취소 주문 풀기 설계

`docs/refund-design.md`의 한계("멈춘 `CANCELING`을 판매자가 풀 방법이 없다")를 메운다.

## 1. 문제

취소·환불은 3단계다(주문 `CANCELING`으로 → 결제사 취소 호출 → 마무리). 결제사 호출이 **결과를 알 수 없게** 끝나면(응답 없음, 5xx) 주문은 `CANCELING`에 남는다. 보통은 웹훅이나 구매자의 "취소 이어서 처리"가 마무리하지만, 결제사(PG)가 취소를 계속 거절하면(예: 이틀 지난 나이스 테스트 결제가 PortOne에는 "결제 완료"로 남고 취소하면 502) 아무도 풀 수 없다. 구매자 화면에는 "취소 처리 중"만 남고, 판매자 화면에는 할 수 있는 버튼이 없다.

## 2. 원칙: 판매자의 말이 아니라 **결제사의 답**으로 푼다

판매자가 "취소됐어요"라고 주장하면 주문을 취소로 바꾸는 방식은 쓰지 않는다. 환불이 안 됐는데 취소로 바꾸면 돈을 잃고, 환불이 됐는데 "결제 완료"로 되돌리면 상품이 공짜로 나간다. 그래서 두 동작 모두 **서버가 결제사에 결제 상태를 직접 조회**(`GET /payments/{id}`, 트랜잭션 밖)하고, 그 답이 허용하는 일만 한다.

| 결제사의 결제 상태 | "취소 상태 확인" | "취소 포기" |
|---|---|---|
| `CANCELLED`(전액 취소) | 주문을 마무리한다(`CANCELLED`+재고 복구, 또는 `REFUNDED`). 웹훅과 같은 경로 | **거절**(409). 이미 취소됐으니 "취소 상태 확인"을 안내 |
| `PAID`(결제 완료) | 아무것도 바꾸지 않고 "아직 취소되지 않았어요(PAID)"를 알려 준다 | 주문을 취소 요청 전 상태로 되돌린다(`PAID`/`SHIPPED`/`DELIVERED`) |
| 그런 결제가 없음(404) | 아무것도 바꾸지 않고 "결제 정보가 없어요"를 알려 준다 | **거절**(409). 404는 PortOne 주소·비밀키를 잘못 설정했을 때도 나므로 "결제가 없다"를 믿고 되돌리지 않는다(환불된 주문이 결제 완료로 돌아가면 상품이 공짜로 나간다) |
| 결제는 있는데 상태 값이 비어 있음 | 바꾸지 않고 "알 수 없음(`UNKNOWN`)" | **거절**(409) |
| `PARTIAL_CANCELLED` 등 그 밖의 상태 | 바꾸지 않고 상태를 알려 준다 | **거절**(409). PortOne 콘솔에서 직접 확인하도록 안내 |

- **"취소 포기"는 결제사가 정확히 `PAID`라고 답하고, 그 결제의 주문 번호와 상점이 이 주문과 같을 때만** 한다(웹훅·"취소 상태 확인"이 `CANCELLED`를 믿을 때 하는 것과 같은 확인).
- 결제 설정(API 비밀키, 상점 id)이 비어 있으면 두 동작 모두 503(결제 기능 꺼짐)이다.
- 결제사가 준 상태 문자열은 영문·숫자·밑줄만 남기고 40자까지만 로그·응답에 쓴다.
- 이미 끝난 주문(`CANCELLED`/`REFUNDED`)을 "취소 상태 확인"하면 결제사에 묻지 않고 그 상태를 200으로 돌려주며 `providerStatus`는 비운다(확인하지 않았다는 뜻).
| 조회 실패(응답 없음·5xx) | 503, 아무것도 바꾸지 않는다 | 503, 아무것도 바꾸지 않는다 |

## 3. API (`ADMIN`, `SELLER`, 기존 `/api/admin/orders` 아래)

| 요청 | 설명 |
|---|---|
| `POST /api/admin/orders/{id}/cancel/check` | **취소 상태 확인**. 주문이 `CANCELING`이어야 한다. 이미 `CANCELLED`/`REFUNDED`면 그 상태를 그대로 200으로(멱등). 그 밖의 상태는 409 `INVALID_ORDER_STATE`. 응답 `{ "status": "...", "providerStatus": "CANCELLED\|PAID\|NOT_FOUND\|..." }`. 결제사가 `CANCELLED`면 마무리하고 새 상태를 돌려준다. 아니면 상태는 `CANCELING` 그대로 |
| `POST /api/admin/orders/{id}/cancel/abandon` | **취소 포기**. 주문이 `CANCELING`이어야 한다(아니면 409 `INVALID_ORDER_STATE`). 결제사가 `PAID` 또는 결제 없음일 때만 `revertCancel`로 되돌리고 응답 `{ "status": "<원래 상태>", "providerStatus": "..." }`. `CANCELLED`면 409 `CANCEL_ALREADY_DONE`, 그 밖의 상태면 409 `CANCEL_PROVIDER_STATE`(메시지에 상태 포함) |

- 두 요청 모두 본문이 필요 없다. 응답에는 `Cache-Control: no-store`.
- 상태 바꾸기는 기존 `PaymentTransactions`의 짧은 트랜잭션(`FOR UPDATE`)을 쓴다. 결제사 조회는 그 **밖**에서 한다(`OrderCancelService`의 3단계와 같은 방식). 마무리는 이미 멱등이다(`applyCancelled`는 이미 끝난 주문을 건드리지 않는다).
- 조회와 되돌리기 사이에 구매자의 "취소 이어서 처리"가 결제사 취소를 성공시킬 수 있다. 그 경우 주문이 이미 원래 상태로 돌아갔어도 이어서 오는 `Transaction.Cancelled` 웹훅이 주문을 취소로 마무리한다(기존 동작: `PAID`에서도 `CANCELLED`+재고 복구). 이 짧은 창은 허용한다.
- 로그 한 줄(INFO): 주문 id, 동작(`check`/`abandon`), 결제사 상태, 결과 상태, 수정한 사람(`Authentication.getName()`). 개인정보는 남기지 않는다.
- 결제사 조회 실패의 503은 기존 `PaymentProviderUnavailableException` 처리를 그대로 쓴다. 결제 설정이 꺼져 있으면(`!gateway.isConfigured()`) 기존처럼 `PaymentNotConfiguredException`.

## 4. 화면 (`/admin/orders`)

- `CANCELING` 줄에 "결제사 응답 확인이 필요해요" 안내와 버튼 두 개: **취소 상태 확인**, **취소 포기**.
- 취소 상태 확인: 누르면 요청 중에는 비활성. 결과가 마무리(`CANCELLED`/`REFUNDED`)면 그 줄의 상태가 바뀌고, 아니면 줄 안에 안내를 보여 준다. 예: "결제사에서는 아직 취소되지 않았어요(결제 완료). 취소를 다시 시도하거나 '취소 포기'로 원래 상태로 돌릴 수 있어요."
- 취소 포기: 줄 안 확인 단계("결제사에서 아직 취소되지 않은 경우에만 주문을 원래 상태로 되돌려요. 계속할까요?" + "포기 확정" / "닫기"), 환불 폼과 같은 방식. 거절되면(409) 서버 안내 문구(이미 취소됨 / PortOne 상태 확인)를 줄 안에 보여 준다.
- 오류: 401/403은 기존 방식(로그아웃), 503은 "결제사 응답이 없어요. 잠시 뒤 다시 시도해 주세요."

## 5. 알고 두는 한계

- 이 기능은 판매자가 **누르는** 방식이다. 멈춘 주문을 자동으로 찾아 마무리하는 주기 작업(스케줄러)은 이번 범위가 아니다(다음 작업 후보).
- 포기한 주문은 원래 상태로 돌아가지만 구매자에게 환불은 되지 않았다. PG가 취소를 거절한 주문의 실제 환불(계좌 이체 등)은 판매자가 PG 밖에서 처리한다.
- 구매자 화면의 "취소 처리 중" 안내와 "취소 이어서 처리" 버튼은 바꾸지 않는다(포기하면 주문 상태가 돌아가므로 자연히 사라진다).
