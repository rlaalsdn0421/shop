# 멀티 에이전트 개발 방식

기능을 만들 때 **개발 에이전트가 구현하고, 리뷰 에이전트가 검증하고, 메인 Claude가 결과를 정리해서 사람에게 보고**합니다. 머지와 배포 같은 되돌리기 어려운 결정은 항상 사람이 합니다.

## 에이전트 9개

| 구분 | 에이전트 | 역할 | 정의 위치 |
|---|---|---|---|
| 개발 | `backend-dev` | `backend/` 구현(Spring Boot, Flyway 마이그레이션 포함) | `.claude/agents/backend-dev.md` |
| 개발 | `frontend-dev` | `frontend/` 구현(Next.js 16, 폼, 세션) | `.claude/agents/frontend-dev.md` |
| 개발 | `test-writer` | 테스트 파일만 작성(운영 코드는 수정하지 않음) | `.claude/agents/test-writer.md` |
| 리뷰 | `java-reviewer` | 백엔드 코드: 정확성, 계층, 트랜잭션, 동시성 | 설치된 ecc 플러그인 |
| 리뷰 | `react-reviewer` | 프론트 코드: 훅/상태, 접근성, 계약 일치 | ecc 플러그인 |
| 리뷰 | `database-reviewer` | 마이그레이션 SQL: 기존 데이터, 락, 롤백, 롤링 배포 | ecc 플러그인 |
| 리뷰 | `security-reviewer` | 인증 흐름, 비밀 노출, 권한 | ecc 플러그인 |
| 리뷰 | `pr-test-analyzer` | 테스트가 실제 동작을 지키는지, 빠진 테스트 | ecc 플러그인 |
| 리뷰 | `code-reviewer` | 프론트·백엔드·배포 설정 사이의 일관성 | ecc 플러그인 |

이와 별개로 push할 때마다 도는 자동 리뷰 봇(`scripts/review-loop.sh`)이 마지막 안전망으로 남아 있습니다.

## 진행 순서

1. **계약 먼저**: 메인 Claude가 변경할 API(요청·응답 필드, 상태 코드, 오류 메시지)와 DB 변경을 한 장으로 확정합니다. 프론트와 백엔드가 맞물리는 작업에서 가장 중요한 단계입니다.
2. **병렬 구현**: `backend-dev`와 `frontend-dev`가 각자 자기 영역만 구현합니다(서로 파일이 겹치지 않게 별도 작업 폴더/브랜치를 씁니다). 이어서 `test-writer`가 테스트를 보강합니다. 개발 에이전트는 커밋·푸시를 하지 않습니다.
3. **통합과 검증**: 메인 Claude가 결과를 합치고 전체 테스트·린트·타입체크를 돌립니다.
4. **리뷰**: 변경 종류에 맞는 리뷰어를 **읽기 전용**으로 병렬 실행합니다(예: DB 마이그레이션이 있으면 `database-reviewer`, 인증이면 `security-reviewer`).
5. **보고와 결정**: 메인 Claude가 리뷰 결과를 심각도별로 정리해 보고하고, **고칠지/머지할지는 사람이 결정**합니다.

## 지키는 규칙

- 개발 에이전트는 자기 영역 밖의 파일을 고치지 않고, 계약이 모호하거나 바꿔야 하면 추측하지 않고 질문으로 돌려보냅니다.
- 저장소는 공개이므로 비밀번호, 실제 이메일, 키는 코드·테스트·문서에 넣지 않습니다.
- 이미 적용된 DB 마이그레이션은 수정하지 않고 새 버전을 추가합니다.
- 리뷰어의 의견은 참고 자료일 뿐이고, 반영 여부는 메인 Claude가 근거를 확인한 뒤 사람에게 보고해서 정합니다.

## 쓰지 않는 경우

오타, 문구, 한 파일짜리 수정처럼 작은 일은 에이전트를 나누면 설명하는 비용이 더 큽니다. 메인 Claude가 직접 처리하고, 필요하면 리뷰어만 붙입니다.

## 알아둘 점

- 에이전트 정의(`.claude/agents/`)는 Claude Code 세션을 시작할 때 읽습니다. 새로 추가했다면 세션을 다시 시작해야 선택지에 나타납니다.
- 에이전트를 나누면 느려지고 토큰 비용이 늘어납니다. 대신 구현한 쪽과 검증하는 쪽이 분리되어, 작성자가 놓친 문제를 다른 관점이 잡아냅니다.
