# 오픈 전 법적·정책 체크리스트

이용약관(`/terms`), 개인정보 처리방침(`/privacy`), 교환·환불·배송 안내(`/refund`), 하단 푸터, 회원가입 동의가 코드로 들어가 있다.
아래는 **사용자가 오픈 전에 직접 해야 하는 일**이다.

## 1. 사업자 정보 입력 (Vercel 환경변수)

Vercel 프로젝트의 Environment Variables(Production)에 넣고 **다시 배포**한다. `NEXT_PUBLIC_*`는 빌드할 때 코드에 박혀서, 값을 바꾸고 재배포하지 않으면 화면에 반영되지 않는다.

| 키 | 내용 | 표시되는 곳 |
|---|---|---|
| `NEXT_PUBLIC_BIZ_NAME` | 상호 | 푸터, 이용약관 |
| `NEXT_PUBLIC_BIZ_CEO` | 대표자 | 푸터, 이용약관 |
| `NEXT_PUBLIC_BIZ_REG_NO` | 사업자등록번호 | 푸터, 이용약관 |
| `NEXT_PUBLIC_BIZ_MAIL_ORDER_NO` | 통신판매업 신고번호 | 푸터, 이용약관 |
| `NEXT_PUBLIC_BIZ_ADDRESS` | 주소 | 푸터, 이용약관 |
| `NEXT_PUBLIC_BIZ_PHONE` | 전화 | 푸터, 이용약관, 교환·환불 안내(신청 방법) |
| `NEXT_PUBLIC_BIZ_EMAIL` | 이메일 | 푸터, 이용약관, 교환·환불 안내(신청 방법) |
| `NEXT_PUBLIC_PRIVACY_OFFICER` | 개인정보 보호책임자 이름 | 푸터, 개인정보 처리방침 |
| `NEXT_PUBLIC_PRIVACY_OFFICER_CONTACT` | 책임자 연락처 | 푸터, 개인정보 처리방침 |

- 앞의 7개(사업자 정보)는 **하나라도 비면 푸터와 이용약관의 사업자 정보는 전부 숨겨진다.** 일부만 보이는 일은 없다. 공백만 있는 값도 빈 값으로 본다.
- 예외: 교환·환불 안내의 "신청 방법"은 전화와 이메일을 **각각** 따로 판단한다. 설정된 것만 보이고, 둘 다 없으면 그 절이 통째로 빠진다.
- 보호책임자 2개는 이름과 연락처가 **둘 다 있어야** 보인다. 없으면 처리방침의 해당 항목이 통째로 빠진다.
- **보호책임자 연락처는 사실상 필수다.** 처리방침은 열람·정정·삭제·처리정지 요구를 보호책임자에게 하라고 안내하는데, 비어 있으면 화면 어디에도 그 요구를 할 경로가 없다.
- 값이 비어 있으면 화면에는 아무것도 나오지 않는다(임시 값·"준비 중" 표시 없음). 오픈 전에 반드시 채워서 화면에 나오는지 확인한다.

## 2. 해야 할 신고·지정·확인

1. **사업자등록과 통신판매업 신고**가 필요하다(온라인으로 상품을 파는 사업이면 통신판매업 신고번호를 화면에 표시해야 한다). 신고 후 1번의 키를 채운다.
2. **개인정보 보호책임자를 지정**한다(위 1번 참고).
3. **국외 이전 수신자별 연락처와 이전 방법을 처리방침에 적는다.** 현재 처리방침에는 이전받는 자(Neon, Google, Vercel, Upstash), 국가, 항목, 목적, 보유기간만 있고 **수신자 연락처는 확인되지 않아 적지 않았다.**
4. **실제 리전을 확인한다.** Neon, Cloud Run, Vercel, Upstash 각각 콘솔에서 확인한다. 처리방침은 Neon·Google은 싱가포르, Vercel은 "싱가포르 등", Upstash는 "아시아 지역 데이터센터"로만 적었다. 저장소 README에는 us-east1(Ohio)로 옛 표기가 남아 있어 실제와 다르다(처리방침은 싱가포르 기준). Upstash는 실제 국가를 확인해 방침에 적는다.
5. **호스팅 로그 보관기간을 확인**한다(Vercel, Google Cloud 로그). 확인한 기간을 처리방침 "보유·이용 기간"에 반영한다. 지금은 "각 업체의 정책에 따름"으로만 적혀 있다.
6. **Neon 백업·PITR(시점 복구) 보존기간을 확인**하고 처리방침에 반영한다. 처리방침은 탈퇴 시 "서비스에서 복구할 수 없도록 익명화"하되 "업체 백업에는 일정 기간 남을 수 있다"고 적었다. 실제 보존기간이 정해지면 숫자를 적고, 설정을 줄일 수 있으면 줄인다.
7. **상품 이미지 호스트를 확인**한다. 처리방침은 판매자가 등록한 외부 이미지 서버에 방문자 접속 정보가 전달될 수 있다고 적었다. 시드 데이터는 `picsum.photos`를 쓴다. 실서비스에서는 쓸 이미지 호스트를 정하고 필요하면 방침에 호스트를 적는다.
8. **가입 동의 기록(일시, 약관 버전)의 보관기간을 정한다.** 처리방침은 분쟁 대응용 증빙으로 탈퇴 후에도 보관하고 "기간을 정해 파기하는 절차는 준비 중"이라고만 적었다. 기간을 확정해 방침에 쓰고 파기 절차를 만든다.

## 3. 문구 검토

- **이용약관·개인정보 처리방침·교환·환불 안내의 문구는 일반적인 서식을 바탕으로 작성한 초안이다. 오픈 전에 변호사 또는 법무 전문가의 검토를 받기를 권한다.** 특히 책임 제한, 약관 변경 공지 기간(7일/30일), 청약철회 제한 사유, 개인정보침해신고센터·분쟁조정위원회 안내(118, 1833-6972), 보유기간 표기, 탈퇴 후 남는 정보 설명을 확인한다.
- 약관·방침을 고치면 시행일(`frontend/src/lib/policy.ts`의 `POLICY_VERSION`, 화면 표기는 여기서 만들어진다)과 백엔드가 기록하는 정책 버전을 **같이** 바꾼다.

## 4. 아직 구현되지 않은 것 (알고 오픈할 것)

1. **배송비는 안내 문구만 있고 주문 금액에는 아직 반영되지 않았다.** 상품 카드·약관·환불 안내는 "3,500원, 50,000원 이상 무료"라고 하지만 주문 합계에는 적용되지 않는다. 다음 PR에서 반영할 예정이고, **반영 전에는 오픈하지 않는다.**
2. **기존 가입자 재동의 절차가 없다.** 이 기능 이전에 가입한 계정은 동의 기록(일시, 정책 버전)이 비어 있다. 새 약관 시행 후에도 재동의를 받지 않는다.
3. **주문 개인정보 파기 배치가 없다.** 처리방침은 보관기간이 지난 뒤 파기하며 자동 파기는 준비 중이라고 밝혔다. 5년이 되기 전에 구현해야 한다. 가입 동의 기록 파기도 같다.
4. **결제(PG)가 없다.** 이용약관은 현재 결제 기능이 없고 주문은 접수만 된다고 사실대로 적었다. 결제를 붙일 때는 약관(결제 수단·절차), 처리방침(PG사에 대한 위탁·국외 이전, 결제 기록 항목), 환불 안내를 함께 고치고 시행일과 정책 버전을 올린다.
5. **주문 취소·교환 신청 기능이 없다.** 교환·환불은 연락처(전화·이메일)로만 받는다. 그래서 1번의 연락처가 비어 있으면 신청할 방법이 없다.
6. **미추적 `frontend-app/`(가입 폼 포함)은 현재 백엔드와 호환되지 않는다.** 동의 필드(`termsAgreed`, `privacyAgreed`)를 보내지 않아 가입이 400으로 거절된다. 이 폴더가 어디에 배포되는지 확인하고, 쓰지 않으면 정리한다.

## 5. 구현되어 있는 것

- 만 14세 미만은 가입할 수 없다(생년월일 검증).
- 가입 시 이용약관과 개인정보 수집·이용에 모두 동의해야 하고, 동의 일시와 정책 버전이 서버에 기록된다.
- 회원 탈퇴 시 아이디·이메일·비밀번호·생년월일이 익명화되고 로그인이 막힌다. 주문 기록은 보관된다.
- 주문 재시도 키는 브라우저 sessionStorage에 이름·연락처·주소 평문 없이 해시값으로만 저장되고, 로그아웃과 탈퇴 때 지워진다.
