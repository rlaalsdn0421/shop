# 상품 수정(관리자) 설계

`docs/product-options-design.md`의 PR 4. 지금까지는 상품을 **만들기만** 하고 고칠 수 없었다. 옵션 재고를 채우고, 취소·반품된 재고를 맞추고, 가격을 바꾸려면 필요하다.

## 1. 범위

| 수정할 수 있다 | 수정할 수 없다(이번 범위 밖) |
|---|---|
| 이름, 설명, 카테고리, 해시태그, 이미지(1~10장, 순서) | 옵션 추가·삭제·색상·사이즈 이름 변경 (주문 기록이 옵션을 가리킨다) |
| 가격, 정가(할인 전 가격), 재고 | 상품 삭제, 판매 중지(숨김) |
| 옵션이 있으면 **옵션별** 가격, 정가, 재고 | 옵션이 있는 상품을 옵션 없는 상품으로(또는 반대로) 바꾸기 |

- 권한은 기존 `/api/admin/**`와 같다(`ADMIN`, `SELLER`).
- 옵션이 있는 상품의 `products.price`/`original_price`는 가장 싼 옵션 값, `price_varies`는 옵션 가격이 모두 같지 않으면 true, `products.stock`은 0이다(등록 때와 같은 규칙). 수정할 때마다 **다시 계산**한다.

## 2. API

`PUT /api/admin/products/{id}` (전체 교체, 응답 `{ "id": "..." }`)

```json
{
  "name": "...", "description": "...", "category": "의류|null",
  "hashtags": ["a", "b"], "imageUrls": ["https://...", "..."],

  "price": 12000, "originalPrice": 15000, "stock": 8, "expectedStock": 10,

  "options": [
    { "id": "옵션 id", "price": 12000, "originalPrice": null, "stock": 3, "expectedStock": 5 }
  ]
}
```

- **옵션이 없는 상품**: `price`, `stock`, `expectedStock`이 필수, `originalPrice`는 선택. `options`는 비어 있거나 없어야 한다(있으면 400).
- **옵션이 있는 상품**: `options`에 그 상품의 옵션을 **빠짐없이 한 번씩**(모르는 id, 중복, 빠진 id는 400). 최상위 `price`/`originalPrice`/`stock`/`expectedStock`은 없어야 한다(있으면 400).
- 이름·설명·카테고리·해시태그·이미지는 등록과 같은 검증(`ProductValidation`: 이름 200자, 설명 2000자, 카테고리 허용 목록, 해시태그 최대 3개, 이미지 1~10장). 가격 ≥ 0, 정가는 없거나 판매가보다 커야 하고, 재고 ≥ 0, `expectedStock` ≥ 0. 옵션 값은 `normalizeOptions`의 가격·정가·재고 규칙과 같다.
- `imageUrls[0]`이 대표 이미지(`products.image_url`)가 된다. `product_images` 행은 통째로 다시 쓴다(`sort_order` = 목록 순서).
- 없는 상품은 404, 검증 실패는 400, **재고가 그 사이 바뀌었으면 409**(`code: STOCK_CHANGED`, 메시지 "그 사이 재고가 바뀌었어요. 새로고침한 뒤 다시 입력해 주세요.").

## 3. 재고: 숫자 직접 입력 + 낙관적 확인

관리자는 창고에서 센 실제 수량을 그대로 입력한다. 입력하는 사이 주문이 들어와 재고가 바뀌면, 그 숫자로 덮어쓰면 팔린 만큼이 되살아난다. 그래서 화면이 불러온 값을 `expectedStock`으로 같이 보내고, 서버는 **잠근 행의 현재 재고가 `expectedStock`과 다르면 아무것도 저장하지 않고 409**를 준다.

- 재고를 바꾸지 않은 항목(`stock == expectedStock`)은 현재 값과 달라도 건드리지 않고 비교도 하지 않는다. 다른 필드만 고치는 저장이 주문 때문에 막히지 않게 하려는 것이다.
- 한 요청 안의 한 항목이라도 충돌하면 전체를 되돌린다(한 트랜잭션).

## 4. 잠금과 트랜잭션

- 한 트랜잭션. 먼저 **상품 행을 `PESSIMISTIC_WRITE`로 잠근 뒤**(`em.find(..., PESSIMISTIC_WRITE)`), 옵션 행을 **`StockKey`와 같은 순서(옵션 id 문자열 오름차순, `String.compareTo`)로 한 행씩** `em.find(..., PESSIMISTIC_WRITE)`로 잠근다. 주문 생성·취소·만료가 같은 `StockKey` 순서로 재고 행을 잡으므로, 같은 순서를 지켜야 교착이 없다.
- **이 순서가 교착을 만들지 않는 이유는 잠금 종류에 달려 있다.** 주문은 옵션 행을 먼저 잡고(재고 차감 UPDATE), 맨 마지막에 `order_items`를 넣는데, 그 행이 상품·옵션을 외래키로 가리켜 Postgres가 그 행들에 `FOR KEY SHARE`를 건다. 수정이 상품 행을 일반 `FOR UPDATE`로 잡고 있으면 주문은 상품 행을, 수정은 옵션 행을 서로 기다려 교착이 난다. Hibernate 6.5.3은 Postgres에서 `PESSIMISTIC_WRITE`를 `FOR NO KEY UPDATE`로 보내고(`org.hibernate.SQL` 로그로 확인, 일반 `for update`는 0건), 이 잠금은 `FOR KEY SHARE`와 충돌하지 않아 교착이 없다. `ProductEditIntegrationTest`의 "주문이 옵션을 잡은 채 `order_items` 삽입 직전에 멈춘 사이에 수정이 들어오는" 시나리오가 이를 고정한다. Hibernate나 방언을 바꿔 잠금 종류가 달라지면 그 테스트가 먼저 실패한다.
- 옵션 행을 `SELECT ... ORDER BY id ... FOR UPDATE` 한 문장으로 잠그지 **않는다**. DB 정렬 규칙(collation)이 Java 문자열 순서와 다를 수 있어 잠금 순서가 어긋난다.
- 잠근 뒤 읽은 값이 현재 값이므로, 재고 비교(`expectedStock`)와 수정은 엔티티 필드에서 한다. 재고 변경용 `@Modifying` UPDATE를 같은 트랜잭션에서 섞지 않는다(영속성 컨텍스트가 낡은 재고를 다시 써서 덮어쓰는 것을 막는다).
- 설정 값: `SET LOCAL lock_timeout = '3s'`(주문 쪽과 같다). 잠금 대기 시간 초과는 기존 처리처럼 503류로 간다(구현은 기존 `OrderCancelService`/`PaymentTransactions`의 방식을 따른다).
- 이미지: 기존 `product_images` 행을 지우고 새로 넣는다(같은 트랜잭션). 옛 상품(행 없음)도 수정하면 행이 생긴다.

## 5. 가격 경쟁(설계 문서 PR 4 주의 항목의 결론)

주문은 상품·옵션 행을 **잠그지 않고 읽어** 가격을 정한 뒤 재고를 차감하고, 주문 줄과 총액, 결제 금액은 모두 그 읽은 가격에서 나온다. 가격 수정이 그 사이에 끼어들어도 한 주문 안의 줄·총액·결제 금액은 서로 맞는다(주문이 가격 수정 직전에 일어난 것으로 본다). 결제 금액 검증은 상품을 다시 읽지 않고 주문 총액으로 한다. 그래서 `AND price = :expected`를 재고 차감에 넣는 변경은 하지 않는다(주문 경로를 건드리는 위험이 이득보다 크다). 리뷰에서 이 판단을 반박하면 다시 정한다.

화면의 가격이 수정 직후 잠깐 옛 값일 수 있는 것(페이지 캐시, 장바구니에 담아 둔 가격)은 6절에서 다룬다.

## 6. 화면

- `/admin/products` 목록의 각 줄에 "수정" 링크(접근 가능한 이름 "수정 - {상품 이름}") → `/admin/products/{id}/edit`.
- 수정 화면은 공개 상세 API(`GET /api/products/{id}`)로 값을 채운다(이미지, 옵션 id, 옵션 재고, 상품 재고가 이미 들어 있다). 새 조회 API는 만들지 않는다.
- 옵션 없는 상품: 이름, 설명, 카테고리, 해시태그, 이미지, 가격, 정가, 재고. 옵션 있는 상품: 위 공통 항목 + 옵션 표(옵션 이름은 읽기 전용, 옵션별 가격·정가·재고 입력).
- 저장하면 성공 안내 후 목록으로, 409면 안내 문구와 "새로고침" 버튼(다시 불러오기).
- 입력 검증은 서버와 같은 규칙으로 화면에서도 먼저 한다(등록 화면과 같은 방식).
- 장바구니 가격은 이번에 건드리지 않는다(7절 한계).

## 7. 알고 두는 한계

- 옵션 추가·삭제·이름 변경, 상품 삭제·판매 중지는 없다. 옵션이 잘못 등록되면 새 상품으로 다시 등록해야 한다.
- 재고 수정은 별도 감사 테이블에 기록하지 않는다. 서버 로그 한 줄(상품 id, 수정한 사람, 이전·이후 판매가, 바뀐 재고 값 개수)만 남는다. 상품에 판매자 소유 정보가 없어서 `SELLER`와 `ADMIN`은 모든 상품을 고칠 수 있다(등록과 같은 권한 모델).
- **같은 상품을 두 사람이 동시에 고치면 재고를 뺀 나머지는 마지막 저장이 이긴다.** 재고만 `expectedStock`으로 보호한다. 이름·가격·이미지는 나중에 저장한 값이 앞의 값을 덮는다(버전 토큰은 두지 않았다).
- **재고 상한은 1,000,000개다.** 복구는 `stock + 수량`(int)이라, 21억을 입력하면 이후 취소·만료가 숫자 넘침으로 실패한다. 등록 화면과 수정 화면, 서버가 모두 같은 상한을 쓴다.
- 옵션이 50개면 잠금과 UPDATE가 100문장쯤 된다(커넥션 5개 중 하나를 그동안 쓴다). 잠금 대기는 `lock_timeout` 3초로 끝난다. 문제가 되면 `hibernate.jdbc.batch_size`를 켠다.
- **장바구니 가격이 옛 값일 수 있다.** 장바구니(`localStorage`)는 담을 때의 가격을 보여 주고, 주문 금액과 결제 금액은 서버가 새로 계산한 값(`totalAmount`)을 쓴다. 가격을 수정하면 둘이 다를 수 있다. 결제창에는 서버 금액이 뜨므로 잘못 결제되지는 않지만, 주문 직전에 "가격이 바뀌었어요"를 알려 주는 안전장치가 필요하다. 이 PR에는 넣지 않고 다음 작업으로 둔다(주문·결제 흐름을 건드리므로 따로 설계한다).
- 공개 상품 화면은 캐시하지 않는다(`fetch`가 `no-store`이거나 Next.js 기본값이라 저장하지 않음). 수정 직후 바로 반영된다. 목록 일부(`api.ts` 194행)가 어떤 설정인지는 구현 때 확인한다.
